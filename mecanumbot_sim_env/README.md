# mecanumbot_sim_env

Simulation environment for the project (part 1): the Mecanumbot in Gazebo
Fortress with the full Nav2 stack, Nav2 configuration, test maps, start/goal
scenarios, and a harness that runs the real Nav2 Planner Server on a static map
so the planners can be compared quickly.

## Contents

| Path | What |
| --- | --- |
| `config/nav2_params.yaml` | Full Nav2 Humble config (robot footprint, inflation, holonomic DWB, AMCL, all planners) |
| `config/harness_overrides.yaml` | Static-map-only global costmap for the harness |
| `behavior_trees/` | One NavigateToPose tree per planner, plus navigate-through-poses |
| `maps/` | `AI_dept` and `LED_exp` lab maps, plus five generated `test_*` maps (see `maps/README.md`) |
| `scenarios/` | Fixed start/goal pairs per map |
| `launch/planner_harness.launch.py` | map_server + planner_server + fixed TF, no simulator |
| `launch/navigation.launch.py` | Full Nav2 stack on the `/mecanumbot/...` topics |
| `launch/sim.launch.py` | Gazebo + robot + Nav2, the whole simulation in one command |
| `models/mecanumbot/` | Gazebo model of the robot (body, LD08 lidar, velocity control, odometry) |
| `rviz/harness.rviz` | Map, costmap and one coloured path per planner |
| `rviz/sim.rviz` | Map, costmaps, lidar, footprint and plans, with the 2D Goal Pose tool |

## Planner IDs

Planner Server loads one instance per criterion, so the criterion is chosen per
request and nothing has to be restarted:

| planner_id | Plugin | Mode |
| --- | --- | --- |
| `Shortest` | `mecanumbot_path_planner/AStarPlanner` | shortest |
| `Safest` | `mecanumbot_path_planner/AStarPlanner` | safest, `safety_preference: 1.0` |
| `Smoothest` | `mecanumbot_path_planner/AStarPlanner` | smoothest, `smoothness_preference: 1.0` |
| `Combined` | `mecanumbot_path_planner/AStarPlanner` | combined, both preferences `1.0` |
| `NavFn` | `nav2_navfn_planner/NavfnPlanner` | stock Nav2 baseline (Dijkstra) |

- `ComputePathToPose`: set `planner_id` in the goal.
- `NavigateToPose`: set `behavior_tree` to the matching
  `behavior_trees/navigate_to_pose_<id>.xml`. The default is `Shortest`.

## Running the simulation

In the dev container (see `docs/docker.md`), after `cb`:

```bash
ros2 launch mecanumbot_sim_env sim.launch.py map:=AI_dept
```

RViz opens in the browser desktop (http://localhost:6080/vnc.html). Click
**2D Goal Pose**, press on the spot where the robot should go and drag to set
its final heading, and the robot drives there. (The press point is the goal,
not the end of the drag.)
Launch arguments:

| Argument | Default | Meaning |
| --- | --- | --- |
| `map` | `AI_dept` | map name in this package or a path to a map yaml |
| `x`, `y`, `yaw` | start of the first scenario pair | where the robot spawns, map frame |
| `localization` | `none` | `none`: map = odom (odometry is exact in Gazebo); `amcl`: run AMCL |
| `gui` | `false` | also open the Gazebo window (slow without a GPU) |
| `rviz` | `true` | open RViz |

The Gazebo world is generated from the map when the launch starts
(`make_world`), so the walls in the simulator are exactly the occupied cells of
the map. Any map that works with map_server works here too.

To pick the planner, send the goal with the matching behavior tree, for example:

```bash
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: -1.16, y: -2.63}, orientation: {w: 1.0}}},
    behavior_tree: $(ros2 pkg prefix mecanumbot_sim_env)/share/mecanumbot_sim_env/behavior_trees/navigate_to_pose_safest.xml}"
```

Goals clicked in RViz use the default tree (`Shortest`).

The robot model is deliberately simple: the base is moved by Gazebo's
VelocityControl system (no wheel or roller physics), so it follows
`/mecanumbot/cmd_vel` exactly, including sideways motion. Odometry has no drift.
That is enough to compare paths and driving time; it is not a model of the
real robot's wheel slip.

## Test maps

Besides the two lab maps there are five small maps made so that the criteria
disagree in a known way. They are generated by `make_test_maps.py` (layouts in
metres, deterministic), which also writes their scenario files.

| Map | Layout | What it shows |
| --- | --- | --- |
| `test_gap_vs_detour` | a block with a 2 m long, 0.7 m wide passage and a wide opening at the top | Shortest takes the passage, Safest the detour |
| `test_slalom` | 12 m corridor, four baffles from alternating sides | how much each planner turns |
| `test_cluttered` | 8×8 m room with 12 pillars (fixed seed) | clearance and turning among many similar routes |
| `test_dead_end` | U-shaped trap opening towards the start | no planner gets stuck; search time |
| `test_open_room` | empty 8×8 m room | baseline, all planners should agree; sideways and turned goals |

Their starts and goals have different headings, so turning on the spot and
sideways driving show up too. After changing a layout:

```bash
cd /ws/src/mecanumbot-path-planner/mecanumbot_sim_env
python3 -m mecanumbot_sim_env.make_test_maps        # all maps, or --only test_slalom
cb
```

The script refuses to write a map if a start or goal ends up closer than
0.4 m to a wall.

## Recording drives in Gazebo

`drive_scenarios` drives every start/goal pair of a map with every planner and
records what happened. Start the simulation on the same map first:

```bash
# terminal 1
ros2 launch mecanumbot_sim_env sim.launch.py map:=test_slalom

# terminal 2
cd /ws/src/mecanumbot-path-planner
ros2 run mecanumbot_sim_env drive_scenarios test_slalom
```

Before each run the robot is moved to the start pose in Gazebo (and AMCL is
told where it is, if it runs), the costmaps are cleared, and the goal is sent
with that planner's behavior tree. A run that takes longer than `--timeout`
simulated seconds (default 180) is cancelled and counted as failed.

Output in `results/drive_<map>_<time>/`:

| File | Content |
| --- | --- |
| `summary.csv` | per run: `success`, `duration_s` (sim time), `planned_length_m` (first plan), `driven_length_m`, `final_error_m` (distance to goal at the end), `replans` |
| `runs/<pair>_<planner>.csv` | the driven trajectory at 50 Hz: `t, x, y, yaw` in the map frame, `vx, vy, wz` from odometry in the robot frame, and `cmd_vx, cmd_vy, cmd_wz`, the command sent to the base |
| `paths.json` | planned and driven path of every run |
| `<pair>.png` | driven paths (thick) over planned paths (thin) |

The trajectory files have what an energy or time estimate needs (sideways
speed `vy` included). Computing those estimates is part of the evaluation, not
of this package.

Useful options: `--planners Shortest Safest`, `--only full_slalom`,
`--timeout 120`, `--no-images`. A full map takes a while: every run is a real
drive in simulated time, roughly 20-60 s each.

## Running the harness

In the dev container (see `docs/docker.md`), after `cb`:

```bash
# terminal 1
ros2 launch mecanumbot_sim_env planner_harness.launch.py map:=LED_exp rviz:=true

# terminal 2, from the repository folder so results land in ./results
cd /ws/src/mecanumbot-path-planner
ros2 run mecanumbot_sim_env plan_scenarios LED_exp
```

`plan_scenarios` prints a table and writes `results/<map>_<time>/` with
`results.csv`, `paths.json` and a PNG per start/goal pair. Useful options:
`--planners Shortest Safest`, `--only wp1_to_wp4`, `--no-images`.

Columns: `length_m` is the polyline length, `planning_time_ms` is reported by
Planner Server, `total_turn_deg` sums absolute heading changes, and
`mean_cost`/`max_cost` are global costmap values (0–100) under the path points.
These are quick sanity numbers, not the final evaluation metrics.

## Colours

In RViz (both `sim.rviz` and `harness.rviz`) the map is white for free
space, black for walls and grey-green for unknown space. The costmaps are
drawn see-through on top: light blue/lavender turning pink and red is the
safety margin around obstacles (redder is costlier), the cyan line marks
where the robot's body would touch an obstacle, and magenta/dark purple is
the obstacle itself. `docs/getting-started.md` explains this in more detail.

In the simulation (`sim.rviz`): green outline = robot footprint, red dots =
lidar points, blue line = global plan of whichever planner is in use, orange
line = local plan.

In the harness (`harness.rviz`) and in all result pictures, each planner has
its own colour:

| Colour | Planner |
| --- | --- |
| Blue | Shortest |
| Green | Safest |
| Red | Smoothest |
| Purple | Combined |
| Orange | NavFn |

In the pictures the start is a black circle and the goal a red circle, and a
planner marked "(failed)" in the legend found no path (`plan_scenarios`) or
did not reach the goal (`drive_scenarios`). Drive pictures show the driven
path as a thick line and the planned path as a thin, lighter line in the same
colour.
